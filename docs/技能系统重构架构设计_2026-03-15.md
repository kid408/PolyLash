# 技能系统重构架构设计（2026-03-15）

## 1. 设计目标

本轮重构的目标不是继续堆角色脚本，而是把技能系统稳定成以下架构约束：

- `PlayerBase` 只做输入枢纽、角色切换与 F 装配。
- `SkillManager` 只做技能槽，不再拼装技能语义。
- `Q / E / F` 都有统一抽象基类，但允许角色保留专属行为。
- 技能上下文与留场资产脱离临时节点存活，可被切人继承、调试读取、F 窗口消费。
- 旧的编号式原型、`f_modes` 与 `skill_ultimate_qef_v3.gd` 已退出主链；当前兼容只剩少量 `player meta` 兜底。

## 2. 新目录与职责

```text
scenes/
  skills/
    skill_q_base.gd            # Q 语义基类：画线、闭合、Q 资产注册、Q -> F 通知
    skill_e_base.gd            # E 语义基类：读取 Q 上下文、发布 E 上下文
    skill_f_base.gd            # F 语义基类：开窗、tick、消费 Q/E 语义资产
    skill_context_packet.gd    # 统一上下文包
    skill_asset_registry.gd    # 留场资产注册表
    skill_context_bridge.gd    # 上下文/资产发布与查询桥
    skill_manager.gd           # Q/E/LMB/RMB 槽位管理
    skill_ultimate_base.gd     # F 共享运行时基类
    players/
      skill_<role>_q.gd        # 可读 Q 入口
      skill_<role>_e.gd        # 可读 E 入口
      f_roles/skill_<role>_f.gd
                               # 可读 F 入口
      skill_saw_path.gd        # 复杂 Q runtime（内部实现）
      skill_web_weave.gd
      skill_fire_path.gd
      skill_lurewarden_loop.gd
      skill_mine_path.gd
      skill_wind_path.gd
```

## 3. 六层结构

### 3.1 输入层

文件：

- `scenes/unit/players/player_base.gd`

职责：

- 接收 `Q / E / F / LMB / RMB`
- 将 Q/E/LMB/RMB 转给 `SkillManager`
- 单独装配 F 脚本
- 转发 `notify_q_path_executed` 给当前 F

约束：

- 通用输入逻辑收敛回 `player_base.gd`
- 角色脚本不再复制标准 `_handle_input()`

### 3.2 技能槽层

文件：

- `scenes/skills/skill_manager.gd`

职责：

- 读取 `player_skill_bindings.csv`
- 实例化 Q/E/LMB/RMB
- 管理冷却、消耗、切人快照
- 输出 `get_semantic_runtime_snapshot()`

约束：

- 不根据角色玩法语义做分支
- 不持有 Q/E/F 的隐式联动状态

### 3.3 技能语义层

文件：

- `skill_q_base.gd`
- `skill_e_base.gd`
- `skill_f_base.gd`

职责：

- `Q`：定义“画线 -> 结算 -> 发布 Q 上下文 / Q 资产 -> 通知 F”
- `E`：定义“读取最近 Q -> 执行二次操作 -> 发布 E 上下文 / E 资产”
- `F`：定义“开窗 -> tick -> 响应 Q -> 消费 E/Q 资产 -> 发布 F 运行时剖面”

### 3.4 上下文与资产层

文件：

- `skill_context_packet.gd`
- `skill_asset_registry.gd`
- `skill_context_bridge.gd`

职责：

- 统一上下文包结构
- 统一留场资产注册、过期清理、最近项查询
- 统一 Q/E/F 上下文读写
- 向调试层输出可读快照

关键设计：

- `asset_id` 绑定创建时间与角色归属
- 查询顺序优先走“当前上下文挂接的资产”，再回落到注册表
- 资产排序统一按 `created_msec` 倒序

### 3.5 效果层

文件：

- `SkillEffectManager`

职责：

- 负责墙体、区域、debuff zone 等效果实体
- 不做 Q/E/F 语义判断，只执行语义层给出的效果参数

### 3.6 配表与调试层

文件：

- `config/player/player_skill_bindings.csv`
- `config/player/ult_config.csv`
- `config/player/skill_params_wide*.csv`
- `scenes/arena/debug_switcher.gd`

职责：

- 配表驱动角色 -> Q/E/F 装配
- 统一技能 ID、脚本名与调试显示主键
- 显示上下文、资产数、F 运行计数与反馈字段
- 支撑录制/回放验收

## 4. 运行时流转

### 4.1 Q 流程

```text
PlayerBase 输入 Q
  -> SkillManager.execute_skill("q")
  -> role Q script / Q runtime
  -> SkillQBase._cache_q_execution_context(...)
  -> SkillContextBridge.publish_q_context(...)
  -> SkillAssetRegistry.register_asset(...)
  -> PlayerBase.notify_q_path_executed(...)
  -> 当前 F.on_q_path_executed(...)
```

### 4.2 E 流程

```text
PlayerBase 输入 E
  -> SkillManager.execute_skill("e")
  -> role E script
  -> SkillEBase.get_recent_q_context / get_recent_q_asset
  -> 角色执行二次操作
  -> SkillEBase.publish_e_context(...)
  -> SkillContextBridge.publish_e_context(...)
  -> SkillAssetRegistry.register_asset(...)
```

### 4.3 F 流程

```text
PlayerBase 输入 F
  -> PlayerBase 加载/激活 role F script
  -> SkillFBase._on_ultimate_activated()
  -> 定时 tick -> _apply_mode_signature("tick")
  -> Q 完成后 on_q_path_executed(...)
  -> _apply_mode_signature(line/closure)
  -> _apply_q_link_signature(line/closure)
  -> SkillContextBridge.publish_f_context(..., f_role_id)
```

## 6. 关键设计决策

### 6.1 不把 F 并入 SkillManager

原因：

- F 不是普通技能槽，而是独立的 10 秒兑现窗口系统。
- F 需要比 Q/E 更高的运行时剖面、激活/停用钩子与 Q 路径事件响应。

结论：

- `SkillManager` 继续只管 Q/E/LMB/RMB。
- `PlayerBase` 单独装配 F。

### 6.2 F 主链彻底收敛到 SkillFBase

原因：

- 旧单体把模式判断、角色特判、效果生成、上下文缓存混在一起，继续保留只会制造新的兼容债务。
- `f_roles/skill_<role>_f.gd` 已经足够承接角色差异，没必要再保留编号模式入口。

结论：

- 所有角色 F 均进入 `SkillFBase` + wrapper 体系。
- `f_modes` 与 `skill_ultimate_qef_v3.gd` 已从主链清退。

### 6.3 E/F 联动优先用语义资产，不再优先依赖 `player meta`

当前规则：

- `E` 发布窗口资产，例如 `butcher_hook_window`、`weaver_recall_window`
- `F` 优先通过 `SkillContextBridge.get_recent_e_asset()` 查询窗口
- 老的 `player meta` 只做兼容兜底，不再是唯一数据源
