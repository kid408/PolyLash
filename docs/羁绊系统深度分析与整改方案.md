## 一、现有系统架构全景

| 管理器 | 文件路径 | 职责 |
|--------|----------|------|
| BondManager | `autoloads/bond_manager.gd` | 羁绊核心逻辑：标签统计、等级激活、属性加成、机制效果查询 |
| BondUILoader | `autoloads/bond_ui_loader.gd` | 羁绊UI数据加载、图标管理、队伍羁绊统计（选择界面用） |
| EquipmentManager | `autoloads/equipment_manager.gd` | 角色装备管理（每角色1个道具槽） |

| ModifierManager | `autoloads/modifier_manager.gd` | 标签驱动的数值修改器系统（Tier 2 道具用） |
| ShopManager | `autoloads/shop_manager.gd` | 波次间商店，消耗品购买 |

### 1.2 配置文件

| 文件 | 路径 | 内容 |
|------|------|------|
| bond_config.csv | `config/player/bond_config.csv` | 12个羁绊定义，每个最多3级 |

| item_effect_config.csv | `config/item/item_effect_config.csv` | 道具效果详细配置 |
| shop_item_config.csv | `config/item/shop_item_config.csv` | 商店消耗品（18种，含权衡型） |

### 1.3 羁绊体系结构

#### 三类羁绊标签

```
Origin（身世）: inkborn(魔导), colossus(重装), nomad(游侠), alchemist(后勤)
Mastery（职能）: blaster(爆破师), architect(筑墙者), hexer(咒术师), geometrist(几何学家)
Tactic（战术）: assist(支援型), vanguard(突击型), commander(指挥型)
```

#### 每个角色携带3个标签

以 `player_config.csv` 为例：
```
butcher  → colossus(重装) + architect(筑墙者) + vanguard(突击型)
pyro     → inkborn(魔导)  + blaster(爆破师)  + vanguard(突击型)
weaver   → inkborn(魔导)  + hexer(咒术师)    + assist(支援型)
```

#### 激活阈值（bond_config.csv）

| 等级 | Origin/Mastery需求 | Tactic需求 |
|------|-------------------|------------|
| Lv.1 | 2个相同标签 | 2个相同标签 |
| Lv.2 | 4个相同标签 | 4个相同标签 |
| Lv.3 | 6个相同标签 | 无（Tactic只有2级） |

### 1.4 三层道具系统

```
Tier 1 - 属性道具: 直接加数值（+50HP, +50速度, +10攻击）
Tier 2 - 魔法道具: 通过ModifierManager添加百分比加成（火焰+20%, 冰霜+25%）
Tier 3 - 圣物道具: 提供额外羁绊标签（武道圣物→martial标签）
```

### 1.5 数据流

```
角色选择 → 统计羁绊标签 → BondManager.recalculate_active_bonds()
                                    ↓
                            检查每个标签数量 vs 激活阈值
                                    ↓
                            激活满足条件的羁绊等级
                                    ↓
                    stat_mod效果 → apply_stat_modifiers() → 修改玩家属性
                    mechanic效果 → has_mechanic() / get_mechanic_value() → 技能代码手动查询
```

## 二、问题诊断：为什么羁绊系统"没什么用"

### 2.1 致命问题：圣物系统是断路的

这是最核心的问题。代码中存在明确的 TODO 注释：

```gdscript
# bond_manager.gd 第 89-92 行
# TODO: 处理圣物提供的额外羁绊标签
# for relic in equipped_relics:
#     if relic.has("bond_tags"):
#         for tag in relic.bond_tags:
#             current_bond_counts[tag] = current_bond_counts.get(tag, 0) + 1
```

**圣物道具（Tier 3）虽然可以装备，但装备后提供的羁绊标签从未被 BondManager 读取。**

`PlayerBase._apply_tier3_item()` 只是打印了一行日志，没有实际注册到 BondManager：
```gdscript
func _apply_tier3_item(item_data: Dictionary) -> void:
    # 注意：这里只是存储 item_id，实际的羁绊标签应用由 BondManager 处理
    if OS.is_debug_build():
        print("[PlayerBase] 注册圣物: 提供羁绊标签 '%s' x%d" % [target_tags, value])
```

而 `PlayerBase.get_equipped_relic_tags()` 虽然实现了，但 **没有任何地方调用它**。

**结论：圣物系统完全不工作。玩家装备了圣物，但羁绊标签数量不会增加，羁绊等级不会提升。**

### 2.2 严重问题：圣物标签与羁绊标签不匹配

`item_effect_config.csv` 中的圣物提供的标签：
```
relic_martial   → martial
relic_arcane    → arcane
relic_survivor  → survivor
relic_destruction → destruction
relic_velocity  → velocity
relic_control   → control
```

`bond_config.csv` 中实际存在的羁绊标签：
```
inkborn, colossus, nomad, alchemist
blaster, architect, hexer, geometrist
assist, vanguard, commander
```

**两套标签完全不匹配！** 即使圣物系统修好了，`martial`、`arcane`、`survivor` 这些标签在 bond_config 中根本不存在，不会激活任何羁绊。

同样，`item_config.csv` 中的圣物标签也有问题：
```
巨擘圣物 → colossus  ✅ 匹配
墨灵圣物 → inkborn   ✅ 匹配
炼金圣物 → alchemist ✅ 匹配
爆破圣物 → blaster   ✅ 匹配
...
```

但 `item_effect_config.csv`（实际被代码读取的文件）用的是另一套标签名。**两个配置文件的圣物数据不一致。**

### 2.4 中等问题：stat_mod 效果的应用时机不确定

`BondManager.apply_stat_modifiers()` 方法存在，但需要外部主动调用。从代码搜索来看，**没有找到在战斗开始时统一调用此方法的地方**。羁绊的属性加成（如重装+25%生命、游侠+15%速度）可能根本没有生效。

### 2.5 中等问题：队伍上限与羁绊阈值的矛盾

- 队伍最多6个角色
- 每个角色3个标签 → 最多18个标签
- Origin 有4种，Mastery 有4种，Tactic 有3种
- Lv.3 需要6个相同标签

**在6人队伍中，要凑齐6个相同 Origin 标签，意味着所有6个角色都必须是同一 Origin。** 这在实际游戏中几乎不可能，因为：
1. 每个 Origin 只有约8个角色
2. 玩家需要兼顾 Mastery 和 Tactic 的搭配
3. 没有圣物系统的辅助（因为圣物不工作）

**Lv.3 羁绊在当前设计下几乎不可达。**

### 2.6 轻微问题：UI 显示不一致

选择界面显示 `count/max` 格式，战斗界面显示 `Lv.X` 格式。这个问题在 `bond-level-display-fix` spec 中已经记录。

## 三、竞品分析

### 3.1 《云顶之弈》(Teamfight Tactics) - 羁绊系统标杆

**核心机制：**
- 每个英雄携带2-3个羁绊标签
- 羁绊有多个激活阈值（如2/4/6/8）
- **纹章（Emblem）道具**：可以给任意英雄添加一个羁绊标签
- 纹章通过合成获得，是凑高级羁绊的关键手段

**为什么有效：**
1. 纹章让玩家有"破格"手段，不必完全依赖角色自带标签
2. 高级羁绊（6/8人）效果极其强力，值得围绕构建
3. 每个羁绊等级的效果差异明显，Lv.1 是基础增益，Lv.3 是改变玩法的机制
4. 羁绊之间有协同效应，鼓励混搭

**对比 PolyLash 的差距：**
- PolyLash 的圣物 = TFT 的纹章，但圣物系统不工作
- PolyLash 的 Lv.3 几乎不可达，TFT 通过纹章+选秀可以合理达到
- TFT 的羁绊效果层层递进且有质变，PolyLash 的 Lv.1/Lv.3 都是同类型加成（只是数值不同）

### 3.2 《弹壳特攻队》(Survivor.io) - 轻量羁绊

**核心机制：**
- 装备套装效果：2件套/4件套激活不同加成
- 装备可以自由搭配，不绑定角色
- 套装效果简单直接：攻击+X%、暴击+Y%

**为什么有效：**
1. 套装效果直观，玩家立刻能感受到数值变化
2. 2件套门槛低，容易激活
3. 4件套是明确的构建目标

**对比 PolyLash 的差距：**
- PolyLash 的 stat_mod 效果（如+25%生命）可能没有正确应用
- 玩家无法直观感受到羁绊带来的变化

### 3.3 《吸血鬼幸存者》(Vampire Survivors) - 武器协同

**核心机制：**
- 武器+被动道具的组合触发进化
- 进化后武器获得质变效果
- 组合关系明确，有图鉴可查

**为什么有效：**
1. 组合效果是"质变"而非"量变"
2. 玩家有明确的构建路线图
3. 进化后的视觉反馈极其强烈

**对比 PolyLash 的差距：**
- PolyLash 的 mechanic 效果（如"闭合图形变牢笼"）本质上就是质变效果，但没有实现
- 缺少视觉反馈让玩家感知羁绊激活

### 3.4 竞品对比总结

| 维度 | 云顶之弈 | 弹壳特攻队 | 吸血鬼幸存者 | PolyLash（现状） |
|------|---------|-----------|-------------|-----------------|
| 羁绊激活门槛 | 合理（有纹章辅助） | 低（2件套） | 低（2件组合） | **过高（Lv.3需6人，圣物不工作）** |
| 效果感知度 | 高（UI+数值+机制） | 中（数值明显） | 极高（武器进化） | **极低（大部分未实现）** |
| 构建策略深度 | 极高 | 中 | 高 | **低（缺少有效的构建手段）** |
| 道具辅助系统 | 纹章系统完善 | 装备自由搭配 | 被动道具丰富 | **圣物系统断路** |
| 视觉反馈 | 强（羁绊激活动画） | 中 | 极强（进化特效） | **弱（仅图标变化）** |

## 五、整改方案

### 5.1 整改优先级

```
P0（必须立即修复）: 圣物系统断路 + 标签不匹配
P1（核心体验）:     stat_mod 效果确认生效 + 高优先级 mechanic 实现
P2（体验提升）:     羁绊激活反馈 + UI统一 + 剩余 mechanic 实现
P3（长期优化）:     羁绊阈值重新平衡 + 新羁绊设计
```

#### 5.2.2 打通 BondManager 的圣物标签读取

在 `BondManager.recalculate_active_bonds()` 中，取消 TODO 注释并实现圣物标签统计：

```gdscript
func recalculate_active_bonds(team_player_ids: Array, equipped_relics: Array = []) -> void:
    # ... 原有角色标签统计 ...
    
    # 新增：统计圣物提供的额外标签
    for player_id in team_player_ids:
        var relic_tags = _get_player_relic_tags(player_id)
        for tag in relic_tags.keys():
            current_bond_counts[tag] = current_bond_counts.get(tag, 0) + relic_tags[tag]
    
    # ... 后续激活逻辑不变 ...

func _get_player_relic_tags(player_id: String) -> Dictionary:
    """获取角色装备的圣物提供的羁绊标签"""
    var item_type = EquipmentManager.get_equipped_item(player_id)
    if item_type <= 0:
        return {}
    
    # 从 item_config.csv 读取 bond_grant
    var item_config = WarehouseManager.get_item_config(item_type)
    # 需要扩展 WarehouseManager 读取 bond_grant 列
    var bond_tag = item_config.get("bond_grant", "")
    if bond_tag.is_empty():
        return {}
    
    return {bond_tag: 1}
```

#### 5.2.3 扩展 WarehouseManager 读取 bond_grant

当前 `WarehouseManager._load_item_configs()` 只读取了3列（itemType, description, resourcePath），需要扩展读取第4列 `bond_grant`：

```gdscript
func _load_item_configs() -> void:
    # ... 原有代码 ...
    while not file.eof_reached():
        var line = file.get_csv_line()
        if line.size() < 3:
            continue
        var item_type = int(line[0])
        var description = line[1]
        var resource_path = line[2]
        var bond_grant = line[3] if line.size() > 3 else ""  # 新增
        
        item_configs[item_type] = {
            "description": description,
            "resourcePath": resource_path,
            "bond_grant": bond_grant  # 新增
        }
```

### 5.3 P1：确保 stat_mod 生效 + 高优先级 mechanic（预计 3-4 天）

### 5.4 P2：羁绊激活反馈 + UI 统一（预计 2-3 天）

#### 5.4.1 羁绊激活时的视觉反馈

当羁绊等级提升时（如从 Lv.1 升到 Lv.2），应该有明显的视觉反馈：

1. **全屏闪光**：短暂的颜色闪烁（根据羁绊类型：Origin=绿色, Mastery=红色, Tactic=蓝色）
2. **图标动画**：BondHUD 中对应图标放大弹跳
3. **飘字提示**：屏幕中央显示"【重装】Lv.2 激活！全队生命+25%"
4. **音效**：播放对应的羁绊激活音效（已有 bond_*.wav 音效文件）

#### 5.4.2 属性面板

在角色信息界面增加"羁绊加成"面板，明确显示：
- 当前激活的羁绊及等级

### 5.5 P3：羁绊阈值重新平衡（预计 1 天）

#### 5.5.1 降低激活门槛

考虑到6人队伍 + 圣物系统，建议调整阈值：

```csv
# 修改前
inkborn,origin,1,2,...  # Lv.1 需要2人
inkborn,origin,2,4,...  # Lv.2 需要4人
inkborn,origin,3,6,...  # Lv.3 需要6人

# 修改后（方案A：降低门槛）

inkborn,origin,2,3,...  # Lv.2 需要3人（降低）
inkborn,origin,3,5,...  # Lv.3 需要5人（降低，圣物可补1个）
```

#### 5.5.2 Lv.3 效果应该是"质变"而非"量变"

当前设计中，很多 Lv.3 只是 Lv.1 的数值放大版：

```
重装 Lv.1: 生命+25%
重装 Lv.3: 生命+60%  ← 只是数值更大，没有质变
```

建议参考 TFT 的设计，Lv.3 应该引入新机制：

```
重装 Lv.1: 生命+25%
重装 Lv.2: 画图时霸体
重装 Lv.3: 生命+60% + 受到致命伤害时免死一次（每局1次）  ← 质变效果
```

## 九、总结

PolyLash 的羁绊系统在**设计层面**是完整且有深度的——12个羁绊、3级激活、stat_mod + mechanic 双轨效果、圣物辅助系统——这些设计元素与 TFT 等成熟产品的思路一致。

问题出在**实现层面**：

1. **圣物系统完全断路**（代码有 TODO 未完成，标签名不匹配）
2. **83% 的 mechanic 效果未实现**（设计了24个，只做了4个）
3. **stat_mod 效果的应用链路不确定**（可能没有在正确时机调用）
4. **缺少玩家感知反馈**（激活了羁绊但玩家看不到/感受不到变化）

修复优先级：先通圣物（P0），再确保数值生效（P1），然后补全核心 mechanic（P1-P2），最后优化体验（P2-P3）。

预计总工期：**7-10 个工作日**（P0+P1），完整整改约 **2-3 周**。
