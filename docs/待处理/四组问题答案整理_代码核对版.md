# 四组问题答案整理（代码核对版）

本文基于当前项目代码与配置核对，目标是回答你列出的四组问题，并明确区分：

- `代码已确认`：能直接从脚本 / CSV / 配置读出来。
- `基于代码推断`：能从数值结构推导，但不等于实机手感结论。
- `仍需实机确认`：代码无法单独证明，必须进游戏验证。

补充说明：

- 当前项目里很多核心战斗逻辑是 `_process(delta)` 帧驱动，不是统一走 `_physics_process` 固定物理帧。
- 之前斩铁右键一直报 `NO ENERGY` 的问题，原因是 `space_skill_config.csv` 里 `space_minimalist` 行错位；该行现在已经修正。

## 1. 物理引擎与全局基准

### 1.1 物理 Tick Rate

`代码已确认`

- `project.godot` 里没有显式设置 `physics/common/physics_ticks_per_second`。
- 但更关键的是，当前和这几位角色直接相关的很多逻辑并不依赖固定物理 Tick：
- `scenes/unit/enemy/enemy.gd` 的敌人 AI 主循环跑在 `func _process(delta)`。
- `scenes/effects/phalanx_pinball_arena.gd` 的弹球模拟也跑在 `func _process(delta)`。

`结论`

- 不能把当前实现简单概括成“碰撞伤害固定 60Hz 结算”。
- 如果项目没有别处改引擎默认值，那么 Godot 默认物理 Tick 大概率还是 `60Hz`，但当前这批技能与敌人运动的关键结算更接近“每帧推进 + 局部 CD”，而不是纯物理帧驱动。

`仍需实机确认`

- 不同帧率下，方阵弹球的单位时间伤害是否会出现明显波动。

### 1.2 画线速度上限

`代码已确认`

- 方阵与缚丝右键画线都没有单独的“最大生成像素/秒”硬上限。
- 它们的处理方式是：
- 每帧读一次 `get_global_mouse_position()`。
- 再按 `draw_sample_spacing` 把路径重采样成离散点。
- 当前采样间隔：
- 方阵 `draw_sample_spacing = 10`
- 缚丝 `draw_sample_spacing = 18`
- 斩铁更特殊：右键画线不是跟鼠标轨迹走，而是直接用角色自己的 `global_position` 作为路径目标点。
- 斩铁当前采样间隔 `draw_sample_spacing = 10`。

`结论`

- 方阵 / 缚丝的实际画线速度，主要受鼠标移动速度、输入采样与帧率影响。
- 斩铁的实际画线速度，主要受角色位移速度、冲刺速度与帧率影响。
- 当前没找到独立的“系统底层最大像素/秒生成上限”。

### 1.3 怪物移速锚点

`代码已确认`

- 方阵基础移速：`270`
- 典型快怪：
- `fast_enemy = 235`
- `volatile_spark = 230`
- `dash_beetle = 230`
- 中压区：
- `breaker_enemy = 190`
- `enemy_glutton = 150`
- 慢怪：
- `tank_enemy = 95`
- `temporal_anchor = 80`

`基于代码推断`

- 以方阵 `270` 为参照，`220-235` 这一档已经很接近“闭合窗口明显变紧”的区域。
- `80-95` 这一档则更接近“动作张力开始不足”的区域。

`仍需实机确认`

- “快到无法闭合”和“慢到失去张力”本质是手感结论，代码只能给锚点，不能替代实机判断。

## 2. 方阵（Phalanx）：防秒杀机制

### 2.1 Boss 受击节流

`代码已确认`

- 没找到“Boss 专属弹球受击 i-frame”这类通用机制。
- 但方阵弹球场本身有两层节流：
- `pair_hit_icd = 0.05`：同一对敌人之间的碰撞伤害最短间隔是 `0.05s`
- 每个被追踪敌人还带一个 `wall_icd`，撞墙后也会被重置成 `0.05s`
- 也就是说，当前闭合弹球不是“零冷却无限多段”，而是场内局部 CD 版本。

`重要边界`

- 这是“弹球场逻辑自带节流”，不是“Boss 天生自带弹球无敌帧”。
- 少数 Boss 可能在自己的脚本阶段里暂时进入 `buff_invincible`，例如 `boss_fortress_titan.gd` 的冲刺阶段，但这不是通用 Boss 受击规则。

`结论`

- 当前代码不能支持“Boss 对弹球完全没有任何节流”这个说法。
- 但也不能支持“Boss 有专门的弹球抗秒杀机制”这个说法。
- 真正存在的是：闭合弹球场自身有 `0.05s` 的撞墙 / 对撞伤害节流。

### 2.2 闭合圈最小限制

`代码已确认`

- 方阵闭合判定目前有这些门槛：
- 最小释放总长度：`24`
- 首尾闭合阈值：`60`
- 如果是自交提取闭环，要求环面积 `> 1.0`
- 但对于“首尾接近形成闭合”的普通闭环，没看到额外的“最小包围面积 / 最小等效半径 / 最小圈半径”硬拒绝。

`重要细节`

- 即使圈很小，依然会生成闭合弹球场。
- 小圈不会被系统否决，只会影响两件事：
- 等效半径越小，伤害倍率越接近下限 `0.75`
- 等效半径越小，额外弹跳预算越少
- 但即便如此：
- 伤害倍率仍然有保底，不会低于 `0.75`
- 弹跳预算仍然有保底，不会低于 `2`

`结论`

- 当前系统确实允许“很小的闭合圈”，只要线长够、闭合成功。
- 所以方阵防秒杀的主防线不是“最小面积限制”，而是“弹球场的 0.05s 局部碰撞节流”。

## 3. 缚丝（Silk）：网络链路与定位

### 3.1 伤害共享参数

`代码已确认`

- `soul_link` 普通链接传伤比例：`0.8`
- `soul_link` 强化链接传伤比例：`1.5`
- 传播出去的伤害会带上这些标记：
- `is_shared_damage = true`
- `soul_link_propagated = true`
- `kind = "soul_link_damage"`
- 传播伤害类型是 `true damage`

`结论`

- 当前缚丝的核心共享机制已经实装，而且强化链路确实不是“更久而已”，而是直接把传伤倍率抬到 `1.5x`。

### 3.2 传播过去的伤害会不会触发其他角色被动 / 系统联动

`代码已确认`

- 会继续走标准 `HealthComponent.take_damage(...)` 流程。
- 所以共享伤害可以正常击杀敌人。
- 敌人死亡后，标准死亡链路仍然会触发：
- 能量球 / 经验 / 金币掉落
- `Global.player.on_enemy_killed(self)`
- `BondManager.on_enemy_killed(self, _last_damage_payload)`

`但也有明确的拦截`

- `BondManager.record_damage_event(...)` 一看到 `is_shared_damage = true` 就会直接 `return`
- 所以很多“基于伤害事件二次触发”的系统不会再次连锁：
- 泛用吸血
- AOE 碎片爆裂
- 异常反应炉
- 羁绊全局伤害分摊

`角色级例子`

- 斩铁的击杀返能逻辑要求最后一击 `kind == "minimalist_slash"`
- 所以缚丝传播伤害击杀，不会算成斩铁右键击杀返能

`结论`

- 缚丝共享伤害不是“完全静默伤害”。
- 它保留标准击杀结果，但会故意跳过很多二次伤害联动，避免无限递归或事件爆炸。

### 3.3 挂链手段与低成本补链

`代码已确认`

- 前台角色自身的挂链入口只有两条：
- 右键开线：给线宽内敌人上普通链接
- F：给全场敌人上强化链接
- E 不负责挂链，只负责：
- 扯断当前已有链接
- 对每个已链接敌人造成 `60` 真伤
- 把它们拉拢到一起

`额外说明`

- 在 `player_silk.gd` 里没找到“普攻顺手挂链”或“低成本小技能补链”的前台路径。
- 但助战系统里存在 `silk_empathy_assist`，它也能上链。
- 这属于后台 assist 逻辑，不等于缚丝前台日常循环里就有第三种低成本挂链手段。

`结论`

- 如果只看缚丝本人前台玩法，当前挂链手段确实偏少。
- 这也是为什么一旦 Q 闭合收链或 E 扯链之后，角色会短暂进入“得重新铺网”的空窗。

### 3.4 当前定位更像打火机还是群伤放大器

`基于代码推断`

- 当前实现更偏“群伤放大器 + 条件性团队回能”，而不是纯打火机。

`依据`

- 角色最有辨识度的收益链路，实际写在 `enemy.gd` 的共享伤害传播里。
- F 的价值也是“全场强化链接”，明显偏放大器。
- 闭合收割虽然能回能，但它会清空已有链接，不像纯电池角色那样可持续提供稳定充能。

`结论`

- 如果只看现有代码重心，缚丝更像“先铺网放大，再择机清链补能”的混合型，而不是把 15 点回能当成唯一主卖点。

## 4. 斩铁（Minimalist）：成本与收益公式

### 4.1 耗能规则

`代码已确认`

- 当前右键不是“每 40px 扣 1 点能量”。
- 当前配置是：
- `point_sample_step = 10`
- `energy_cost_per_unit = 0.4`
- `energy_cost_unit_px = 10`
- `draw_energy_soft_cap_length = 900`
- `draw_energy_post_cap_multiplier = 0.45`

`换算结果`

- `900px` 之前：每 `10px` 扣 `0.4`，也就是每像素 `0.04`
- `900px` 之后：每 `10px` 扣 `0.18`，也就是每像素 `0.018`

`重要结论`

- 当前所谓“soft cap”不是长线惩罚，而是长线折扣。
- 也就是说，斩铁现在并不是越画越亏，反而在 `900px` 之后每像素成本更低。

`便于直观理解的例子`

- `800px` 约消耗 `32`
- `900px` 约消耗 `36`
- `1600px` 约消耗 `48.6`

### 4.2 右键基础伤害倍率

`代码已确认`

- 当前右键伤害公式是：

```gdscript
damage_amount = damage * _compute_slash_damage_multiplier(total_length)
```

- 当前角色脚本里的基础 `damage = 40`
- 长度倍率公式是：

```gdscript
0.8 * (1 + width_coeff * 2.5 + long_line_bonus)
```

- 其中：
- `width_coeff = min(total_length / 2500, 1)`
- `long_line_bonus` 在 `800px` 之前为 `0`
- 超过 `800px` 后，接下来 `1600px` 线性抬升，最高额外加成 `0.75`

`直接结论`

- 现在的斩铁并不是“长线只加宽，不加伤”。
- 线长已经明确参与伤害倍率计算。
- 当前参数下，右键理论最高倍率约为 `3.4x`，也就是基础 `40` 最多放大到约 `136`

### 4.3 系统是否支持长度参与动态伤害

`代码已确认`

- 支持，而且已经在用。
- 当前系统里至少有两处已经直接读取 `total_length`：
- 右键 Q：`_compute_slash_damage_multiplier(total_length)`
- F：`_compute_dimension_damage_amount(total_length)`

`结论`

- “按线长做线性或非线性伤害系数”并不是缺失能力。
- 当前框架已经支持，后续如果要继续拉高长线收益，只需要调公式与参数，不需要重做底层。

## 5. 一页结论

- 方阵现在不是“完全零节流秒杀”，而是“允许小闭环 + 弹球场只有 0.05s 局部 CD”，所以仍然存在高压风险，但风险来源已经可以说清。
- 缚丝共享伤害主链路已经真实存在，普通链 `0.8x`、强化链 `1.5x`；问题不在“没有共享”，而在“前台补链手段偏少，清链动作偏多”。
- 斩铁当前右键已经有长度增伤，而且 `900px` 之后还是折扣耗能；它和旧版投诉“长线只加宽不加伤”已经不一样了。
- 敌人速度的“太快 / 太慢”只能先用配置锚点近似定位，最终还是要靠实机手感收口。
