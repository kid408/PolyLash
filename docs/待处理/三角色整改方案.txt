# To Codex: 三角色整改方案 Phase 6.0 - 方阵 / 斩铁 / 缚丝 / 敌人移速基线回收

Codex，这份文档用于替换旧版“伪接口 + 混模块”的整改工单。目标不是凭空新增一套新系统，而是基于当前项目已经存在的真实脚本和数据入口，对 `方阵`、`斩铁`、`缚丝` 三个角色以及全局敌人移速基线做一次可落地的回收整改。

本次整改只允许沿当前项目真实结构推进，不要再写不存在的类、函数签名或 Meta 标记体系。

---

## 一、总执行原则

- 不要新增 `ClosureSystem.gd` 之类的虚构入口。方阵闭合相关整改应落在 `player_phalanx.gd` 与 `phalanx_pinball_arena.gd`。
- 不要使用 `take_damage(amount, source, is_shared_damage, damage_type)` 这种旧式伪接口。当前项目统一走 `HealthComponent.take_damage(value, payload)`，或 `enemy.apply_modifier_damage(...)`。
- 不要引入 `silk_tagged` 这一套新的标记口径。缚丝当前真实口径是 `SilkLinkUtils`、`soul_link`、`soul_link_empowered`。
- 不要把三个角色的整改混在同一个代码块里。每个模块都必须单独写清 `现状问题`、`整改目标`、`实现入口`、`验收点`。
- 文档里的“目标文件”可以写真实入口，但不要再写与项目实际不符的类名和方法名。

当前项目已确认的真实入口如下：

- 方阵：`scenes/unit/players/player_phalanx.gd`、`scenes/effects/phalanx_pinball_arena.gd`
- 斩铁：`scenes/unit/players/player_minimalist.gd`、`scenes/effects/minimalist_slash_scar.gd`
- 缚丝：`scenes/unit/players/player_silk.gd`、`scenes/effects/silk_link_utils.gd`、`scenes/unit/enemy/enemy.gd`
- 全局移速：`config/enemy/enemy_config.csv`、`config/system/game_config.csv`

## 模块一：方阵闭合圈强度降维回收

### 现状问题

- 当前方阵在 `player_phalanx.gd` 中已经会计算闭合区域 `approx_area`，但真正的闭合收益主要仍由 `phalanx_pinball_arena.gd` 的碰撞伤害和反弹次数驱动。
- 现在的闭合收益更接近“按路径长度和碰撞次数堆强度”，而不是按闭合空间的真实几何价值做平滑换算。
- 这会导致大圈在实战里容易因为反弹次数、墙撞和敌人互撞叠加，出现超出预期的瞬时爆发，尤其容易把 Boss 压进异常高收益区。

### 整改目标

- 方阵闭合圈的强度增长必须从“面积平方级体感”降回“线性可控体感”。
- 闭合圈的收益可以随闭合规模变强，但不能让超大圈直接把收益推到失控。
- 中等尺寸闭合圈应成为主力强度区间，极小圈不应废，极大圈不应溢出。

### 实现入口

- 在 `player_phalanx.gd` 保留现有的闭合多边形采样与 `approx_area` 计算。
- 基于 `approx_area` 派生一个“等效半径”或“线性闭合强度系数”，再把该系数传给 `phalanx_pinball_arena.gd`。
- `phalanx_pinball_arena.gd` 中当前真正影响收益的量是：
  - 碰撞伤害倍率 `collision_damage_ratio`
  - 反弹预算 `max_bounces / remaining_bounces`
  - 敌人与墙、敌人与敌人之间的重复命中
- 本次整改应优先改造 `碰撞伤害倍率` 与 `反弹预算` 的成长口径，不要再假设项目里存在一个单独的“闭合圈直接伤害结算器”。

### 实现要求

- 闭合空间强度推荐由 `sqrt(area / PI)` 这类等效半径口径驱动，而不是直接拿面积本体做乘区。
- 反弹预算不要只按路径总长度计算，至少要让闭合面积或等效半径参与闭合圈收益上限。
- Boss 受到的主要压力应来自“可预期的多次碰撞结算”，不是某一帧异常爆发。
- `E/F` 额外逻辑与方阵闭合整改拆开处理，不要把 F 的刚体 Boss 伤害一起塞回这个模块。

### 验收点

- 小型闭合圈仍然有收口价值，不会直接沦为废技能。
- 中型闭合圈是最稳定的收益区间，打普通怪群和精英都成立。
- 超大闭合圈不会因为面积或多次碰撞叠乘出现“秒 Boss”现象。
- 同一局里，方阵闭合收益的强弱差异可以被玩家感知，但不再是指数级跳变。

## 模块二：斩铁长线收益倒挂修正

### 现状问题

- 当前 `player_minimalist.gd` 的 Q 伤害核心来自线长系数，但现有成长已经较早进入封顶区。
- 画线成本仍然持续线性增加，而伤害与宽度收益会更快趋于饱和，导致“越长越贵，但未必越值”的倒挂体验。
- 当前 F 读取的是场上 `MinimalistSlashScar`，但长线对 F 的兑现增益还不够明确。

### 整改目标

- 斩铁必须重新回到“线越长，压迫感越强，兑现越明显”的角色幻想。
- 长线依然要付出代价，但代价曲线不能长期跑赢收益曲线。
- Q、E、F 都要围绕“高质量长线”形成同一条收益链，而不是只有 Q 看长度。

### 实现入口

- Q 主逻辑在 `player_minimalist.gd`：
  - 画线成本：`draw_base_energy_cost`、`draw_energy_cost_per_step`
  - 线宽成长：`_compute_slash_half_width`
  - Q 伤害：`_release_drawing_path` 中的 `damage_amount`
- F 终结逻辑同样在 `player_minimalist.gd`，但兑现对象来自 `minimalist_slash_scar.gd` 的路径与长度缓存。
- 本次整改应保证 `Q 线长` 与 `Scar 资产` 使用同一条长度口径，不要出现 Q 看一套长度、F 再看另一套长度的分裂设计。

### 实现要求

- 线长收益建议拆成两层：
  - 一层给日常 Q 的伤害和压迫宽度
  - 一层给 F 的终结兑现倍率或命中价值
- 画线成本可以继续随长度增长，但需要做缓坡或封顶，避免超长线纯亏。
- 宽度上限可以保留视觉封顶，但伤害收益不应与视觉宽度完全绑死。
- 自断惩罚、长线定帧、击杀返还 E 冷却与能量这些机制保留，它们是角色手感组成，不是本次问题根因。

### 验收点

- `300 - 600px` 与 `800 - 1400px` 的线在实战收益上必须有肉眼可感知差异。
- 玩家画出长线后，不会出现“成本多花一倍，结果体感只强一点点”的情况。
- F 终结必须明显偏爱高质量长线留下的 Scar，而不是只把它当普通施法媒介。
- 斩铁的强度回到“长线兑现”，而不是靠 E 或外置返还能量硬补体验。

## 模块三：缚丝机制口径统一与体验闭环

### 现状问题

- 当前项目里，缚丝的“链接、传导、回能、收束”并不是缺失状态，而是已经分散在多个真实入口里：
  - `player_silk.gd` 负责 Q/E/F 主流程
  - `silk_link_utils.gd` 负责链接标记
  - `enemy.gd` 负责链接后的伤害传播和表现
- 旧文档把它误写成“需要从零补一套 `silk_tagged + take_damage(source, ...)` 机制”，这会直接制造第二套并行系统，后续一定冲突。
- 当前真正的问题应该定义为“机制体验闭环不够清晰”或“数值口径需要统一”，而不是“核心机制完全不存在”。

### 整改目标

- 缚丝只能保留一套灵魂链接系统，所有 Q/E/F 价值都必须围绕这套系统展开。
- Q 开线、Q 闭合、E 收束、F 强化，必须是同一机制链上的四个环节，而不是四个彼此独立的按钮。
- 伤害传播、回能、收割、表现必须统一口径，避免重复结算和双轨实现。

### 实现入口

- Q 开线：`player_silk.gd::_apply_soul_link_line`
- Q 闭合：`player_silk.gd::_execute_harvest`
- E 收束：`player_silk.gd::_activate_convergence`
- F 全图织网：`player_silk.gd::_activate_web_of_destiny`
- 链接标记：`scenes/effects/silk_link_utils.gd`
- 伤害传播与联动表现：`scenes/unit/enemy/enemy.gd::on_health_component_damage_applied`

### 实现要求

- 不要新增 `silk_tagged`、`soul_shatter`、第二套共享伤害入口。
- 所有链接判定都继续使用 `SilkLinkUtils.has_link / apply_link / clear_link`。
- 所有共享伤害都继续走 `enemy.gd` 里现有的 `on_health_component_damage_applied` 传播口径。
- 如果要调数值，应优先回收这几个量：
  - 传导倍率
  - Empowered link 的强化幅度
  - 闭合回能 `harvest_energy_restore`
  - E 的真伤与收束收益
  - F 的持续时间与能量消耗比例
- Q 闭合的职责是“收割已链接目标并回收团队资源”，不要再把它改写成另一种独立爆发技能。
- E 的职责是“切断并收束现有链接网络”，不要让它脱离 Q 独立成立整套主循环。
- F 的职责是“把整张战场拉进链接窗口”，不要只做一个数值放大按钮。

### 验收点

- 开线命中的敌人会稳定挂上链接，并出现一致的视觉反馈。
- 已链接敌人受到有效伤害后，会稳定向其他链接目标传播，不会递归死循环，也不会双重结算。
- 闭合只收割闭合区域内已经挂链的目标，并产生明确的团队回能反馈。
- E 和 F 都是在“放大或兑现现有链接网络”，而不是绕开链接系统另起炉灶。

## 模块四：全局敌人移速基线回收

### 现状问题

- 旧文档把玩家速度写成了固定的 `Base Speed = 200`、`Dash Speed = 500`，这与当前项目事实不符。
- 当前项目里，玩家基础移速是角色表驱动，不同角色差异很大，Dash 也不是单一 500 的全局值。
- 真正需要整改的是 `enemy_config.csv` 中敌人的速度分布与层级，而不是凭空设一条并不存在的单角色锚点。

### 整改目标

- 敌人速度需要围绕当前玩家群体的真实移动能力重新分层。
- 普通怪必须能形成追击压力，但不能让玩家完全没有走位空间。
- 真正逼 Dash 的应是少数高压怪，而不是所有怪默认都贴着玩家跑。
- Boss 的压迫感应主要来自机制和站位，不应只靠粗暴堆基础移速。

### 实现入口

- 单位基础移速：`config/enemy/enemy_config.csv`
- 全局移速缩放：`config/system/game_config.csv`
- 玩家真实移速参考：`config/player/player_config.csv`

### 建议分层

- 重装 / 肉盾 / 堡垒类：`80 - 110`
- 基础近战 / 常规追击类：`140 - 170`
- 高压施压精英：`175 - 205`
- 疯狗 / 刺客 / 冲脸特化类：`220 - 260`
- Boss 常态：`90 - 160`

### 实现要求

- 优先调整 `enemy_config.csv` 的单体速度，不要一上来改全局 `enemy_speed_scale` 把所有敌人一起抬高或压低。
- 如需改 `enemy_speed_scale`，必须同步复核所有高压怪和 Boss，防止“表里调一次，全局再乘一次”导致二次失真。
- 具有冲锋、位移或突进技能的敌人，基础移速可以略低，但技能期速度乘区要保留压迫感。
- Boss 默认不要再依靠纯跑速追人，重点改机制窗口、追击方式和站位压缩。

### 验收点

- 普通怪能逼迫玩家持续走位，但不会让所有角色都像被疯狗永远贴脸。
- 高压怪是明确例外，玩家能感知“这个怪就是要逼我交 Dash”。
- 重装怪和堡垒怪的威胁来自站位、体量和技能，而不是移动速度异常。
- Boss 战的难点主要来自机制，不是单纯比玩家跑得更快。
