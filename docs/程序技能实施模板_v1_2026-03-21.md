# 程序技能实施模板 v1（2026-03-21）

## 1. 文档定位

这份模板不是角色设计稿，而是 `程序实施稿`。

它回答的是：

- 这个技能要挂在哪个系统层实现
- 这个技能实际要生成什么对象
- 这个技能读写哪些上下文和信号
- 这个技能在异常情况下如何降级
- 这个技能如何验收为“实现正确”

它不回答：

- 这个角色为什么有趣
- 这个角色和别的角色相比为什么独特
- 这个角色在整体阵容里为什么成立

上面三件事统一放在角色技能设计文档里处理；本模板只负责把设计翻译成可以落地的程序结构。

---

## 2. 使用原则

### 2.1 一份技能，一份实施稿

每个角色的 `Q / E / F / dash签名联动`，都应该各自拥有单独的程序实施稿。

禁止把整名角色的全部技能混写在一份程序稿里，否则会失去任务拆分价值。

### 2.2 先写 contract，再写数值

程序稿优先确定：

- 输入
- 状态
- 运行时对象
- 判定模型
- 接口读写
- 异常降级
- 验收方式

数值可以后补，但结构不能后补。

### 2.3 先复用现有钩子，再申请新系统能力

当前项目里，优先复用：

- `Q` 基类开放钩子：
  - `_spawn_line_effect(...)`
  - `_spawn_area_effect(...)`
  - `_transform_open_segment_for_execution(...)`
  - `_transform_polygon_for_execution(...)`
- `Q` 执行上下文缓存：
  - `q_ctx_last_center`
  - `q_ctx_last_radius`
  - `q_ctx_last_time_msec`
  - `q_ctx_last_closed`
  - `q_ctx_last_segments`
  - `q_ctx_last_polygons`
- `dash` 联动信号：
  - `dash_started`
  - `dash_active`
  - `dash_finished`

只有当现有钩子确实无法承载时，才允许在本稿中申请新增通用能力。

- 运行时对象
- 判定与位移
- 表现与读图

### 16. 最终实现结论

最后必须用下面 4 句收束：

- 这个技能程序上到底实现成什么
- 它复用了哪些现有系统
- 它新增了哪些必要能力
- 它最关键的 3 个验收点是什么

示例收束：

- “该技能程序上实现为：开放线执行时生成可留场拖拽危险带，并缓存终点为后续 E 消费”
- “主要复用 `Q` 基类开放线钩子与既有执行上下文缓存”
- “新增能力仅为锚点实体的约束逻辑，不扩展公共输入系统”
- “关键验收点为：终点读图清晰、敌人确实被送向终点、切人后资产仍可被消费”

## 4. 这份模板最适合什么时候用

最适合下面三个场景：

1. 角色设计已经拍板，准备交给程序落地
2. 同一个技能需要程序、美术、测试对齐口径
3. 某个角色已经有设计稿，但落地时总反复返工

如果还处在“这个角色到底好不好玩”的阶段，应该先写角色技能设计模板，而不是直接写这份程序模板。
