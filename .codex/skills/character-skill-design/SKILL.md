# 全角色技能设计基础标准

## 1. 文档目的

- 本标准用于约束全角色的技能玩法设计、角色差异性设计、协同设计与玩法验收。
- 本标准回答的是“角色技能应该怎么设计才对”，不是“系统如何实现”。
- 角色设计时必须同时满足两层要求：`玩法成立` 与 `系统口径成立`。
- 角色技能方案必须优先服务三个目标：`主玩法清晰`、`角色玩法唯一`、`切人协同成立`。

## 2. 基础认知

- 开局只上场 `1` 名角色，局内招募或替换到最多 `3` 人。
- 敌人追玩家，`Q 画线` 是主玩法本体。
- `Q 非闭合` 承担日常输出、保命、走位、拉怪与做局。
- `Q 闭合` 负责高价值收口和大面积爽点。
- `E` 是二次介入，不抢 `Q` 的主玩法位置。
- `F` 是终极技能，不承担日常循环职责。
- `F` 在技能设计层的定位是：`用于集中兑现前面做出的局的高价值终极手段`。
- 左键 `dash` 是全角色共享的通用保命位移，不是角色主玩法本体。

## 3. 角色设计必须同时遵守的系统尺子

本节不是要求你在角色文档里展开系统设计，而是提醒你：角色方案必须能落进已经拍板的系统边界内。

### 3.1 统一行动经济口径

- `Q` 成本正式定义为：`线长成本 + 闭合税`。
- `E` 正式采用：`固定成本 + 固定冷却`。
- `dash` 只保留：`低占用、保命优先、轻联动` 的定位。
- 常规经济统一采用：`日常模板 / 高压模板 / 高光模板` 三套预算。
- `Q` 规划态慢时是正式系统特性，角色设计不得破坏其判断价值。

### 3.2 统一测量单位

- 当前项目统一采用：`1U = 600`。
- `Q短线 = 300 = 0.5U`
- `Q中线 = 600 = 1.0U`
- `Q长线 = 900 = 1.5U`
- `超长线 = 1800+ = 3U+`

这套长度分类是预算尺，不是强制限制玩家画线长度。

### 3.3 常规成本基准

- `Q短线成本 = 0.5U`
- `Q中线成本 = 1.0U`
- `Q长线成本 = 1.5U`
- `Q闭合税 = 0.8U`
- `E基准成本 = 1.5U + 固定冷却`
- `dash基准成本 = 0.25U + 短冷却`

角色设计不要求把数值写成 `U`，但你的方案必须能被换算回这套公共尺子。

### 3.4 三套预算模板

#### 日常模板

- `4 次 Q中线非闭合`
- `1 次 Q中线闭合`
- `2 次 E`
- `1 次 dash`
- 预算基准：`B_day = 9.05U`

#### 高压模板

- `2 次 Q短线非闭合`
- `1 次 E`
- `2 次 dash`
- 预算基准：`B_press = 3.0U`

#### 高光模板

- `2 次 Q短线非闭合`
- `1 次 Q中线闭合`
- `1 次 E`
- `1 次 dash`
- 预算基准：`B_glow = 4.55U`

角色技能方案必须回答：

- 这个角色的日常循环是否能自然落进 `日常模板`。
- 这个角色在危险时是否还能保有 `高压模板` 的求生权。
- 这个角色开 `F` 后是否真的有能力把 `高光模板` 打完整。

### 3.5 资源原型边界

常规角色只允许落在以下三种资源原型中：

- `标准型`
- `高储能型`
- `高回能型`

边界如下：

- 资源原型只改节奏形状，不改总强度。
- 所有常规角色的 `30 秒总预算` 不应明显膨胀。
- 不允许同一角色同时显著 `高储能` 又显著 `高回能`。
- 如果角色需要更肥的资源节奏，必须同步付出代价，比如 `E 更贵`、`Q 超长惩罚更重`、`移动更弱`、`闭合税更高`。

### 3.6 E 偏置角色边界

`E 偏置角色` 可以存在，但必须遵守：

- `Q 相关预算 / 日常预算 >= 50%`
- `E 相关预算 / 日常预算 <= 33%`
- `E 偏置角色` 上限可放宽到 `<= 38%`
- `dash 相关预算 / 日常预算 <= 8%`

结构要求如下：

- `E` 的高价值必须优先来自“改写 Q 已经做好的场”。
- 不允许 `E` 脱离 `Q` 独立完成整套主循环。
- 不允许 `E` 同时承担主要输出、主要控制、主要收口三件事。

`E 偏置角色` 只允许把以下一项做成主优势：

- `E 更便宜`
- `E 冷却更短`
- `E 命中后返还少量常规预算`

最多再附带一项弱副优势，不允许三项同时强。

### 3.7 dash 边界

- `dash` 不参与主循环预算争夺。
- `dash` 不承担主要输出职责。
- `dash` 不承担主要收口职责。
- 角色可以和 `dash` 联动，但联动价值不得反客为主。

允许的 `dash` 联动方向：

- 补位
- 穿越自己布好的 `Q` 场
- 触发轻量标记、击退、回位、引爆

不允许的方向：

- 把 `dash` 做成比 `Q` 更重要的输出主键
- 把 `dash` 做成 `F` 窗口的主要收益按钮

### 3.8 F 窗口边界

- `F` 是独立终极资源，不进入常规经济公式。
- `F` 的系统减负目标，是让玩家在 `35% - 40%` 常规能量入场时，仍然能完成一轮高光收口。
- `F` 窗口需要补足的常规预算缺口，公共目标约为 `0.8U - 1.1U`。
- `F` 的减负优先级固定为：`Q闭合税 > Q线长成本 > E条件返还`。
- `dash` 不参与系统级减负。

这意味着角色设计时，`F` 的爽感重点必须是：

- 让玩家从“继续拖怪”切换成“冲回自己做好的场里收”

而不是：

- 单纯加数值
- 单纯给无敌
- 单纯发一个和前面做局无关的大招

## 4. 第一原则：每个角色的玩法必须唯一

- 每个角色都必须拥有不可替代的玩法签名，不能只是同一套结构换皮。
- 角色差异必须优先于数值差异，先区分玩法，再谈强弱和平衡。
- 玩家在一段短实战中，不看角色名，也能说出“这个角色怎么做局、怎么收口、怎么高光”。
- 每个角色都必须同时拥有唯一的 `主循环`、唯一的 `高光兑现方式`、唯一的 `对外协同价值`。
- 只更换元素、颜色、伤害类型、状态名字、范围大小、倍率高低，不算玩法差异。
- 只把“压一坨怪”“铺一片持续区”“点低血目标”“开大打一轮”换个包装，不算角色特色。
- 如果两个角色在核心循环和高光兑现上只是近义重复，则视为同构，必须重做。

## 5. 每个角色必须回答的四个问题

- `Q 开线` 到底如何改写追击关系。
- `Q 闭合` 到底把什么收成什么。
- `E` 的第二道命令到底改了什么。
- `F` 到底在什么时机开、对什么目标开、如何把收益兑现出来。

如果一个角色与另一个角色的大部分答案高度相似，就说明特色不足。

## 6. Q / E / F 的统一职责

### 6.1 Q 非闭合

- `Q 非闭合` 必须是角色最稳定、最常用、最能体现个性的主循环。
- 玩家不开 `F`、不依赖 `Q 闭合`，也必须能靠 `Q 非闭合 + 走位 + dash` 正常游玩。
- `Q 非闭合` 必须改变追击关系，而不只是多一段伤害。
- `Q 非闭合` 必须留下可继续经营的战场资产。
- 这个资产既要能被自己继续利用，也要能被后手角色接住。

### 6.2 Q 闭合

- `Q 闭合` 必须建立在已有开放资产之上。
- `Q 闭合` 的本质是“收局”，不是另起一个无关的新技能。
- `Q 闭合` 必须明显高于 `Q 非闭合` 的日常价值，承担高价值收口和大面积爽点。
- `Q 闭合` 应该值得等待、值得判断时机、值得赌位置。
- 任何角色都不能因为没打出 `Q 闭合` 就变成残废版。

### 6.3 E

- `E` 是二次介入技能，不是主建场技能。
- `E` 单按必须保底，至少能完成一次明确脱困、拆贴脸、拉口子、短换位或目标修正。
- `E` 接在 `Q` 之后时，必须像“第二道命令”，而不是简单补伤害。
- `E` 可以很强，但不能成为角色最主要的建场来源。
- 玩家大部分日常操作决策，仍应围绕 `Q` 展开。

### 6.4 F

- `F` 是终极技能，不承担日常循环职责。
- `F` 的设计目的不是补平时强度，而是在高价值时机集中兑现前面积累的优势。
- `F` 的高光来源不应只是数值爆发，而应来自主导权提升、收益兑现和角色签名行为的放大。
- `F` 的统一体验要求不是字面意义上的“追怪”，而是让玩家从“保守拖怪”转入“主动收账”。
- 每个角色的 `F` 都必须写清三件事：`最佳启动时机`、`主要收益对象`、`收益兑现方式`。
- `F` 必须足以支撑“值得消耗一次共享终极资源”的身份。
- `F` 不应长期稳定压倒其他角色的 `F`，避免共享终极资源退化为单角色垄断。

## 7. 角色协同标准

- 每个角色都必须回答：`我能为别人留下什么价值`
- 每个角色都必须回答：`我最擅长接住别人留下的什么价值`
- 协同只写“价值接力”，不写“固定绑定角色组合”。
- 每个角色至少要稳定提供以下三类价值中的 `2` 类：`空间价值`、`目标价值`、`资产价值`

说明如下：

- `空间价值` 指区域、路径、窄口、危险侧、安全侧、据点、通道、压缩区等可被后手角色继续利用的场面。
- `目标价值` 指低血目标、名单目标、被压缩目标、挂状态目标、露背目标、高价值精英等可被后手角色优先处理的对象。
- `资产价值` 指炮位、虫巢、节点、站点、补给物、引爆点、召唤物等可被后手角色继续借用的资产。

协同必须是开放式的：

- 同一份价值应允许多个角色接住，而不是只服务一个固定搭档。
- 角色不能只提供“自己爽”的收益，而不给后手角色留下可见、可接、可兑现的战场价值。

## 8. dash 的技能设计定位

- 左键 `dash` 是全角色共享的通用保命位移动作。
- `dash` 的主要用途是逃生、躲避、穿位、过险位与高风险操作。
- 角色可以围绕 `dash` 设计联动收益。
- `dash` 联动属于角色增益层，不应成为角色成立的唯一前提。
- 角色差异不得建立在改写通用 `dash` 的基础定位上。

## 9. 全局 Combo 设计标准

- `Combo` 是全角色共用的高操作认证规则，不绑定某个角色。
- `Combo` 不允许设计成固定按键串或固定输入顺序。
- `Combo` 必须和高风险操作、场面经营、时机兑现有关。
- `Combo` 的基础认证采用 `8s` 三印规则：`险印`、`局印`、`收印`

说明如下：

- `险印` 表示玩家在危险局面中完成一次高质量脱困、穿阵、切侧或反切。
- `局印` 表示玩家成功把怪从“正在追你”改成“可处理态”。
- `收印` 表示玩家在已经做好的坏位置上打出一次高价值兑现。

补充要求：

- `F` 可以帮助玩家创造高光，但不能直接白送完整 `Combo`。
- `Combo` 的目标不是奖励背输入法，而是奖励高压下的判断、做局和收局能力。

## 10. 统一禁止项

- 禁止同构换皮。
- 禁止只靠元素和数值变化伪装角色差异。
- 禁止 `E` 抢走 `Q` 的主玩法位置。
- 禁止 `Q 闭合` 变成与 `Q 开线` 无关的独立大招。
- 禁止 `F` 退化成纯增伤、纯无敌、纯清屏或纯爆发按钮。
- 禁止把 `F` 设计成平时不用、只看倍率的空心技能。
- 禁止让角色变成“不闭合就玩不动”或“不开发力窗口就没有体验”。
- 禁止把角色差异建立在改写通用 `dash` 定位上。
- 禁止把协同写成强制固定配队。
- 禁止角色只吃自己留下的收益，完全无法服务后手角色。
- 禁止用更高数值掩盖玩法空心和角色同构。

## 11. 最低验收标准

- 玩家不开 `F` 时，能稳定完成日常循环。
- 玩家单按 `E` 时，能明显感受到保底脱困或场面修正。
- 玩家使用 `Q 非闭合` 时，能明显看出自己在做局。
- 玩家打出 `Q -> E` 时，能明显看出 `E` 是第二道命令。
- 玩家打出 `Q 闭合` 时，能明显看出这是对前面场面的高价值收口。
- 玩家开启 `F` 时，能明显感受到自己开始主动兑现前面做出的局。
- 玩家切人后，下一角色能看懂上一角色留下的价值，并且接得上。
- 玩家观察 `20 秒` 实战片段时，能说出该角色的玩法签名，而不是把它当成其他角色的变体。
- 去掉元素名和数值描述后，该角色仍能靠行为逻辑被识别出来。
- 如果测试者能用另一个现有角色的描述完整替代该角色，则判定为特色不足。

## 12. 角色设计写作模板

每个角色技能文档都必须至少回答以下内容：

- 一句话角色幻想
- 角色的玩法签名
- `Q 非闭合` 的日常循环是什么
- `Q 开线` 如何改写追击关系
- `Q 闭合` 把什么收成什么
- `E 单按` 如何保底
- `E 接 Q` 的第二道命令是什么
- `F` 的最佳启动时机是什么
- `F` 的主要收益对象是什么
- `F` 的收益兑现方式是什么
- 我能为别人留下什么价值
- 我最擅长接住什么价值
- 我的 `dash` 联动高操作点是什么
- 我的自然 `Combo` 路线是什么
- 我与最相近角色的核心差异是什么

## 13. 角色设计的系统自检

在角色文档进入具体数值前，必须先做一轮系统自检：

- 这个角色的常规循环更接近 `标准型`、`高储能型` 还是 `高回能型`
- 这个角色是否需要 `E 偏置`，如果需要，主优势是哪一种
- 这个角色的 `Q` 主循环是否能自然落进 `日常模板`
- 这个角色在低能量状态下是否还能保住 `高压模板`
- 这个角色的 `F` 是否真的在帮助玩家完成 `高光模板`
- 这个角色的 `F` 减负是否优先服务于 `Q闭合税` 和 `Q线长成本`
- 这个角色的 `dash` 联动是否已经越过“轻联动”边界

如果一个角色在这 7 项里有 2 项以上答不上来，说明它还不适合进入技能细化阶段。

## 14. 设计判断原则

- 先判断这个角色“怎么做局”，再判断它“怎么收局”，最后判断它“能给别人留下什么”。
- 如果一个角色的描述离开数值就站不住，说明玩法还没设计出来。
- 如果一个角色的爽点只能靠 `F` 才成立，说明日常循环有问题。
- 如果一个角色只会自己闭环，不会给队友留值，说明协同设计不成立。
- 如果一个角色可以被另一个角色的描述近乎完整替换，说明差异性不成立。
- 如果一个角色在技能层看起来很帅，但放回系统尺子里明显超预算或越位，优先回调概念，而不是硬补特权。

## 15. 单角色实现规格文档标准

本节用于约束“单个角色技能文档”的输出标准。

当用户要求：

- 重写某个角色技能文档
- 生成某个角色的完整技能规格
- 把某个角色写成程序可实施文档
- 逐个角色打磨

则必须切换到 `单角色实现规格文档` 模式，而不是停留在玩法提案模式。

目标标准：

- 文档必须达到 `85% - 90%` 可落地度。
- 即使删除旧代码，程序也能按文档独立复刻角色。
- 文档不得把关键行为留给程序员脑补。

### 15.1 单角色文档的定位

- 文档是 `实现规格`，不是 `灵感提案`、`方向草稿`、`旧方案整理`。
- 文档回答的是“程序应该如何做出这个技能”，不是“这个技能大概想要什么感觉”。
- 文档允许包含：`术语`、`规则`、`公式`、`状态机`、`参数`、`边界`、`验收`。
- 文档禁止包含：`旧实现对照`、`旧代码说明`、`文件名映射`、`代码路径`、`兼容现状说明`、`当前代码事实整理`。
- 文档必须是干净版本，默认以 `角色重做后正式实现` 为口径。

### 15.2 单角色文档必须采用的结构

单角色实现规格文档默认使用以下结构。

若某角色没有完全相同的机制，可以替换成等价章节，但不得删掉“输入、状态、几何、结算、边界、验收”这几类信息。

- `1. 文档定位`
- `2. 角色定位`
- `3. 统一术语`
- `4. 技能特色总览`
- `5. 行动与资源规则`
- `6. Q 技能设计`
- `7. E 技能设计`
- `8. dash / 冲刺联动`
- `9. F 技能设计`
- `10. 边界规则`
- `11. 参数总表`
- `12. 验收用例`

对于主技能段落，默认需要继续细化到下面这个层级：

- `设计目标`
- `输入与状态机`
- `生成数据`
- `逐帧结算`
- `命中 / 捕获 / 链住 / 吸附 / 位移`
- `落地或持续阶段`
- `结束或断链规则`
- `视觉表现`

### 15.3 单角色文档必须回答的程序问题

只要是程序读完后仍可能出现两种以上做法的地方，都必须写死。

至少要明确回答下面这些问题：

- 技能如何输入：按下、按住、松开、取消、失败、退款。
- 状态如何流转：进入条件、退出条件、中断条件、覆盖条件。
- 运行时会生成哪些对象：投射物、区域、锚点、链线、端点、标记。
- 每个对象在创建时要写入哪些运行数据。
- 每一帧的结算顺序是什么。
- 命中判定按什么几何规则结算。
- 多个目标同时满足条件时如何选主目标。
- 是否有人数上限；如果没有，也必须明确写“不设上限”。
- 伤害如何结算：首触、持续、脉冲、落地重结算、补结算。
- 位移如何结算：推、拉、吸、夹回边界，到底是速度位移还是位置修正。
- 目标离开范围、死亡、无敌、离场、对象被替换时如何处理。
- 旧对象与新对象如何替换。
- 何时生成表现，何时断开表现，哪些目标显示链线或标记。

### 15.4 单角色文档的细化粒度要求

对于 `Q / E / F` 中任何一个技能，只要存在以下内容，就必须写成实现规格，而不是一句话带过：

- `飞出去`
- `拉回来`
- `吸住`
- `钉住`
- `链住`
- `限制活动范围`
- `进入区域`
- `位于图形内部`
- `落地后持续工作`
- `与另一个技能联动`

这些描述如果不落成规则，程序一定会出现脑补分歧。

因此必须补出：

- 判定对象是谁
- 判定中心是谁
- 判定半径或图形是什么
- 判定频率是什么
- 先后顺序是什么
- 是否允许重复触发
- 触发后持续多久
- 何时失效

### 15.5 几何与结算规则写法

涉及几何判定时，优先采用明确写法：

- `最近距离`
- `最近点`
- `奇偶规则`
- `边界点`
- `中心点`
- `最大值 / 最小值`
- `归一化方向`
- `位移上限`

涉及结算时，优先采用明确写法：

- `每一帧按下面顺序结算`
- `每累计满 X 秒触发一次`
- `离开范围后计时器立刻清零`
- `只在落地瞬间生成一次名单`
- `后进入目标是否允许补抓`
- `是否补吃上一次重伤害`

禁止使用下面这类模糊写法直接收尾：

- `会把敌人拉回来`
- `会把敌人拴住`
- `范围内敌人受影响`
- `飞出去命中敌人`
- `落地后持续造成效果`
- `命中后优先处理关键目标`

如果写了这些句子，后面必须继续补成程序规则。

### 15.6 单角色文档的术语要求

- 术语必须先统一，再展开技能细节。
- 同一对象只能有一个主术语，避免同一文档里出现多个近义叫法。
- 术语要服务实现，不要写成纯氛围词。
- 若存在数值记号，例如 `A`，必须先定义含义。
- 若存在特殊状态，例如 `回收标记`，必须先定义触发条件、持续时间和移除条件。

### 15.7 单角色文档的禁止项

生成单角色实现规格时，禁止出现以下内容：

- 以 `旧实现 / 当前实现 / 目标实现` 三栏并排对照
- 大段引用现有代码行为来代替正式设计
- 把代码文件名、类名、函数名直接写进技能正文
- 用 `参考现有逻辑`、`按现在代码差不多做` 作为规则
- 只写体验描述，不写结算规则
- 只写数值，不写判定口径
- 只写机制名，不写边界条件

### 15.8 单角色文档的最低实现清单

如果某个单角色文档缺少下面任意 `2` 项以上，就不能视为可实施版本：

- `统一术语`
- `输入规格`
- `状态机`
- `运行数据`
- `逐帧结算`
- `多目标优先级`
- `替换与覆盖规则`
- `断链 / 结束规则`
- `参数总表`
- `验收用例`

### 15.9 单角色文档的验收标准

单角色实现规格写完后，必须自检下面四件事：

1. 程序删掉老代码后，是否仍能按文档独立实现。
2. 不同程序员分别实现时，是否会做出高度一致的版本。
3. 读文档的人是否还需要靠“理解你的意图”去补关键细节。
4. 文档中的 `Q / E / F` 是否已经能直接拆成开发任务。

如果上述任一问题答案仍然是“不能完全确定”，就说明文档还没压到位，必须继续补规则，而不是切下一个角色。
